On the morning of November 23, all 23 open pull requests in [Supermog](/blog/supermog-builds-itself) were stuck. Every one had failed the same `test` check, and the fleet had parked every one as "needs a human". The code in those PRs was fine. The machine running their CI had been writing **1.6 TB a day** to a 1 TB consumer SSD, and the tests were timing out while they waited for the disk.

Our self-hosted CI runs on one box we call sidekick: a 16-core Ryzen 9 9955HX with 60 GB of RAM and a single 1 TB NVMe drive. The night before, an audit had opened about 20 pull requests at once, and all of their CI landed on sidekick together.

This post covers how we tracked the slow tests down to the disk, where the writes were coming from, and what we changed so the box stops wearing out its own drive.

## Every Test Failed the Same Way 🔴

The failures were strange in a useful way. A different set of tests failed on every run, and none of them had anything to do with the PR being tested. Every failure was a test that normally finishes in milliseconds hitting Bun's 5-second timeout. Database tests and webhook tests were taking 6 to 20 seconds.

We pulled the history of every Supermog test job that ran on sidekick between November 19 and 23 and matched each one against how many other test jobs were running at the same moment:

| Test jobs running at once | Jobs | Failed on timeouts |
|---|---|---|
| 1 | 123 | 15% |
| 2 | 53 | 30% |
| 3 | 44 | 59% |
| 4 | 27 | 67% |
| 5 or more | 36 | 100% |

Sidekick ran 16 runner slots. We had settled on 16 on November 13, while tuning the box for [Automate It](https://automate.it.com)'s CI, whose jobs mostly download packages. Since then the same box had picked up a Windows VM, Android emulators, the fleet's own develop and QA lanes, and Supermog's own CI.

## It Wasn't the CPU 🧮

The box keeps its own performance history with `sar`, so we could look at the evening the failures started. The CPU sat 50 to 60% idle the whole time. Memory looked guilty for twenty minutes, when swap hit 100%, and then recovered on its own.

The disk told a steadier story. NVMe utilization climbed about 6 points for every extra concurrent job and reached 75 to 88%, with iowait near 20%. The tests that timed out all write SQLite files and fsync every commit, so each one waited behind every other job's writes.

We cut sidekick to 4 runner slots to stop the bleeding. Then the more useful question came up: why was a CI box writing that much at all?

## The Drive Had Already Lost 9% of Its Life 💾

Sidekick's `sar` history showed the NVMe writing an average of **1.6 TB a day** since November 15, with a peak of 3.3 TB on November 22. The drive's SMART log said 9% of its rated endurance was already used. CI had been running on the box for about two weeks, and we don't know how much of that 9% came before it.

A 1 TB consumer drive is typically rated for a few hundred terabytes of writes over its life. At 1.6 TB a day, that runs out in months. The slow tests were the symptom we noticed first; the drive was the real cost.

## Every Job Rebuilt Its World on Disk 🔁

Our runner slots are built for isolation. Each job gets a brand-new runner container and a brand-new Docker daemon, and both are deleted when the job ends. Fresh containers keep one job's leftovers away from the next. They also mean a job's tools, dependencies and Docker images are written to the SSD from scratch every time, then deleted.

Linux tracks how much each container writes, so we could measure each source:

| Source | Written | Why |
|---|---|---|
| Docker image builds | Up to 10.5 GB per build | Each job's Docker daemon started empty, so every build pulled and unpacked every layer again. Our arm64 images also build under QEMU emulation on this x86 box. |
| The runner's debug log | About 29,000 lines every 2 minutes | The GitHub Actions runner image prints its internal debug log to stdout. The system journal and Docker's log file each kept a copy, and the runner wrote a third copy itself. The journal had grown to 4 GB. |
| Test databases | About 950 MB per test run | Around 300 tests each create a fresh SQLite database, run the full migration (32 tables, 44 indexes) and fsync every commit. The finished database is only 324 KB, but creating it writes about 1.3 MB. |
| Runner tool bundle | 601 MB per job | The runner's bundled Node.js runtimes were copied into a fresh volume before every job, though they only change when the runner image does. |
| `bun install` | About 325 MB per job | Dependencies installed into an empty workspace for every job. |

The Supermog service itself was barely a blip: its containers wrote 7 MB in four hours.

## What We Changed 🔧

The rule behind every fix: anything a job writes and then throws away should live in RAM, and anything that is the same for every job should be written once.

- **Image builds go to Docker slots that keep their images.** Those slots carry an extra `docker` label, keep their daemon's images and BuildKit cache between jobs, and start every job with no containers, volumes or networks left over. Our workflows send image builds there with one repository variable. We started with two of these slots and now run four. ([ci#7](https://github.com/workingdevshero/ci/pull/7), [ci#14](https://github.com/workingdevshero/ci/pull/14), [supermog#1591](https://github.com/workingdevshero/supermog/pull/1591))
- **Each job's `/tmp` is a RAM disk**, and Supermog's test job points its scratch files at it. A full test run peaks at about 205 MB there.
- **The runner's debug log stays off the disk.** One environment variable stops the runner printing it, Docker keeps no log of the runner container, and the runner's own diagnostic files go to RAM. Journal lines from the runner slots dropped from about 29,000 to 68 per 2 minutes. ([ci#9](https://github.com/workingdevshero/ci/pull/9))
- **The tool bundle is copied once per slot** and mounted read-only, so no job can change it for the next one. ([ci#10](https://github.com/workingdevshero/ci/pull/10))
- **The job's workspace, tool cache and `~/.bun` live in RAM.** The checkout, `node_modules` and build output exist only while the job runs. ([ci#10](https://github.com/workingdevshero/ci/pull/10), [ci#11](https://github.com/workingdevshero/ci/pull/11))
- **Tests migrate the schema once and clone it in memory**, with fsync off under `bun test`. That change also speeds up every developer machine that runs the tests. ([supermog#1594](https://github.com/workingdevshero/supermog/pull/1594))
- **Image jobs stopped doing work nobody used.** Check builds no longer export the image they built, publish jobs keep their BuildKit cache between runs, and a merge that doesn't change what runs on our boxes no longer rolls them out. ([supermog#1617](https://github.com/workingdevshero/supermog/issues/1617), [supermog#1616](https://github.com/workingdevshero/supermog/issues/1616), [supermog#1613](https://github.com/workingdevshero/supermog/issues/1613))

We also moved four repositories to [Bun](https://bun.sh) 1.4.5, the current release line built on Bun's Rust port. That wasn't a disk fix, but it turned up two behavior changes worth knowing about: a recursive `rm` that can't delete something now reports `ENOTEMPTY` where it used to report `EACCES`, and `spawnSync` now waits for the child's stdout to close, the way Node does. The second one exposed a stray `sleep 30` our Android emulator script left behind every time it built a snapshot.

## Then We Ran Out of RAM 🧠

Moving files to RAM has a catch we found the hard way. A RAM disk inside a container counts against that container's memory limit. Each runner slot was capped at 8 GB, and a job now carried its `/tmp`, its workspace, its tool cache and its own processes inside that cap. Over one day the kernel killed 38 processes for hitting it.

We raised the cap to 12 GB and cut the box from 16 slots to 12. That held until we asked the fleet to rebase 10 [Automate It](https://automate.it.com) pull requests at once. Each push starts 8 CI jobs, so about 80 jobs landed together. Load reached 260 on a 16-core box, swap filled, and the kernel killed 15 processes in half an hour. The pull requests failed on test timeouts that had nothing to do with their code. Stopping 4 slots brought memory pressure from 88% to 2% within a minute.

One job type was eating most of it. [Jest](https://jestjs.io) sizes its worker pool from the CPU cores it can see, and a container limited to 8 CPUs still sees all 32 of the host's threads. So a single frontend test job could start around 31 workers at about half a gigabyte each. Capping Jest at 4 workers under CI fixed that ([automate-it#1622](https://github.com/workingdevshero/automate-it/pull/1622)). We now nudge pull requests 3 or 4 at a time, and the box runs 10 slots while we watch whether it can take 12 again.

## Results 📉

*The full-day numbers below are from the first day with most fixes deployed. A clean full day with every fix in place is still to be measured.*

The number we track is disk writes per merged pull request, across every repository whose CI runs on sidekick, so a slow day and a busy day compare fairly.

| | Writes per day | Writes per merged PR |
|---|---|---|
| Before (November 15 to 23) | 1.6 TB on average, 3.3 TB peak | 43 to 84 GB |
| November 24 | 651 GB | about 22 GB |

The biggest single jobs shrank the most:

| Job | Before | After |
|---|---|---|
| amd64 check image build | 8.5 GB | 0.08 GB |
| arm64 check image build | 5.2 GB | 2.2 GB |
| Publish image build | about 8 GB | 3 to 4 GB |
| CI runs per merged Supermog PR | about 6 | 2.4 |

On November 25, idle hours wrote about half a gigabyte, and the busiest hour so far, with about 12 fleet jobs running, wrote 13 GB with the disk 9% busy. At 6 runner slots, the last batch of Supermog test jobs all passed in 3 to 4 minutes with no timeouts. On the night this started, the same job took 15 to 21 minutes with 7 or 8 running at once, and nearly every run timed out.

## Our Boxes Stopped Taking New Builds for Eight Hours 🔄

The machines that run Supermog's jobs update themselves. After each merge, the control plane rolls them onto the new build one at a time: it waits until a box is idle, sends it the new image, and checks that the box comes back on the new build. On November 25, no box updated between 14:58 and 23:16 UTC. Eleven builds merged and reached the control plane in that window, and every box stayed where it was. Nothing alerted us. We found it while checking that an unrelated CI change had taken effect.

The rollout picked our MacBook first every time. The MacBook pulled the image, recreated its containers and came back on the old build. After two tries the rollout stopped for the whole fleet, including the three boxes it had never reached. The next merge started a new rollout, which picked the MacBook first again.

The cause was a merge from that afternoon that folded our two container images into one. On each box, a service called the broker pulls a new image and recreates the containers, and the broker that performs an update comes from the build being replaced. The old broker started a helper from the new image and expected it to run as root. The merged image ran as an unprivileged user, so the helper couldn't read the box's configuration file, and the broker fell back to recreating its own container from the inside. We caught it on a Raspberry Pi: the broker stopped itself halfway through, its replacement was created but never started, and the Pi was left with no broker and could run no jobs.

We pointed the new broker tag back at the previous broker image to get the boxes moving, then fixed both problems. The rollout now skips a box that won't update and carries on with the rest ([supermog#1699](https://github.com/workingdevshero/supermog/pull/1699)). The broker image is a real broker image again, and a broker that can't hand off its own update refuses it and keeps serving ([supermog#1701](https://github.com/workingdevshero/supermog/pull/1701)).

## What We'd Do Differently 🧭

- **Measure a box's writes before deciding how many jobs it can run.** CPU and network were the numbers we tuned on, and neither was the limit.
- **Treat "every job starts from nothing" as a cost to budget for.** Decide per directory whether a job's files belong on disk, in RAM, or in a cache that outlives the job.
- **Count RAM disks as memory.** Moving writes to RAM is cheap until every slot does it at once. Size the slot's memory cap for its RAM disks plus its processes, and size the slot count for the box's total.
- **Check what each tool thinks the machine is.** Jest, Playwright and most build tools size themselves by the cores they can see, and a container's CPU limit doesn't change that number.
- **Track one number per unit of work.** Writes per merged PR told us whether a fix worked; raw daily totals mostly told us how busy the day was.
- **Watch the build each box runs.** Every deploy in those eight hours passed its checks. The number that showed the problem was the build each box reported, and nothing was watching it.
- **The old version performs the upgrade.** A service that updates itself has to stay compatible with the previous version's updater for one release, down to which user the new image runs as.
